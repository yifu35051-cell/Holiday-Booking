# 支付与邮件：WireMock + DirectMail

本页是当前配置基线（2026-11-07）。**支付使用本地 WireMock 服务虚拟化，邮件使用已配置的阿里云 DirectMail SMTP。** 开发和 Docker 部署均采用此组合，不再启动 Mailpit，也不需要支付公网 IP、隧道或第三方支付账号。旧 Alipay 适配器留作非默认候选，不是本期验收目标。

## 1. 组件分别负责什么

| 组件 | 实际职责 | 不应误认为 |
| --- | --- | --- |
| WireMock 3.13.2-2 | 创建/查询/授权/关单/退款的 HTTP 契约，逐交易故障注入，转发签名回调 | 银行、独立第三方支付供应商、余额数据库 |
| Spring Boot + MySQL | 独立 PIN、余额、扣/退款流水、持久化渠道状态、业务校验与确认 | WireMock 内存场景能代替资金账本 |
| DirectMail SMTP | 酒店统一发信身份，经 TLS 把邮件交给真实 SMTP 服务 | 给每个用户购买一个互联网邮箱、自动同步外部来信 |
| mail / notification | 前者负责个人站内邮箱和共同传输；后者负责预订确认及 D3/D1 任务 | 两套互相独立的 SMTP 配置 |

WireMock 的普通 HTTP 响应只有 `operation/outTradeNo/decision`，不会直接宣告业务付款成功。授权仍须 PIN 和余额校验；付款成功来自 MySQL 中原子提交的渠道交易及钱包扣款。WireMock 重启不应清空资金记录，实际重启验收仍待执行。

## 2. 一次配置，日常直接启动

真实配置分别放在 `config/development.env`、`config/deployment.env`，不要覆盖已存在的数据库密码。当前工作副本已保留用户提供的 DirectMail 凭据，复制 SMTP 项到部署配置，并为两个环境生成各自的回调/代理随机密钥；没有把凭据写入本文或前端。

关键项如下，示例中的秘密必须自行生成，不能照抄为真实密码：

```dotenv
PAYMENT_MODE=wiremock
WIREMOCK_BASE_URL='http://127.0.0.1:9090'
WIREMOCK_CALLBACK_SECRET='至少32字符的随机秘密'
EMAIL_MODE=smtp
MAIL_HOST=smtpdm.aliyun.com
MAIL_PORT=465
MAIL_USERNAME='已验证的酒店发信地址'
MAIL_PASSWORD='对应SMTP专用密码'
MAIL_FROM='已验证的酒店发信地址'
MAIL_SMTP_AUTH=true
MAIL_SSL_ENABLE=true
MAIL_STARTTLS=false
JOBS_ENABLED=true
EMAIL_DAILY_LIMIT=50
MAIL_RECIPIENT_ALLOWLIST=''
```

Docker 的 WireMock 地址固定为 `http://wiremock:8080`，回调目标为私网 `http://backend:8080`；开发回调目标通过 `host.docker.internal` 指向宿主机后端。部署还要求 `TRUSTED_EDGE_SECRET`，它与回调密钥必须不同。可用 `python -c "import secrets; print(secrets.token_hex(32))"` 单独生成每一个秘密；不要把输出提交到 Git。

首次或本次代码更新后，按[根 README](../README.md)主动打包一次。WireMock 镜像首次缺少时执行 `docker pull wiremock/wiremock:3.13.2-2`。日常命令不构建、不拉取：

```powershell
# 开发：同时启动前后端、MySQL 和 WireMock
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\Start-System.ps1 -Mode Development
# Docker 部署：只启动已准备好的镜像
docker compose --env-file config/deployment.env -f config/compose.yaml up -d --no-build --pull never
```

当前 Docker 引擎未运行，本轮只验证了 Compose 解析；没有宣称 WireMock 容器已下载、已启动或迁移已在工作库执行。旧 Mailpit 容器/卷未删除，停用后不参与新拓扑。

## 3. 一笔支付的完整流程

1. 顾客注册并登录 CUSTOMER 入口，选择房型、日期，取得服务端报价，再创建预订。返回 `PENDING_PAYMENT`、应付单及 15 分钟期限；报价本身不占库存。
2. 首次使用钱包，输入登录密码、六位新 PIN 和确认值。余额从 `0.00 CNY` 开始；模拟充值仅接受 `100.00/1000.00/10000.00`，有额度上限、PIN 和幂等保护。
3. 创建付款尝试时提交服务端应付金额，方式严格为 `Alipay` 或 `Wechat`；二者是模拟标签。WireMock HTTP 接受创建后，MySQL 保存渠道 PENDING 记录。
4. 顾客输入独立 PIN 授权。先在事务外检查 WireMock 授权契约，再在一个数据库事务内校验/扣余额、写渠道 PAID、唯一 PAYMENT 流水及回调事件；任一步失败全部回滚。五次连续密码错误锁 15 分钟。
5. 提交后界面显示等待确认，定时查询业务状态。后台从持久事件队列领取并提交租约，经过 WireMock 转发签名事件；HMAC-SHA256 绑定原始 JSON 和时间戳，允许前后 5 分钟。
6. 回调只提供交易号提示，后端再查渠道实际记录，核对应付金额、交易号、付款时间和业务状态。只有校验成功，才确认预订/会员/补款改订；重复回调不重复推进。主动查询和后台对账走同一校验。
7. 关闭付款尝试不等于取消预订。未知渠道状态不释放库存；取消/改订至少提前 24 小时，取消全额退款，改订补退差价。退款沿用稳定退款号，累计不能超过实付，原钱包没有付款流水的历史演示付款不会凭空增加余额。

### 主要请求契约

所有路径加 `/api/v1`；顾客会话与 CSRF 必需。写请求中标注的幂等键由调用方提供，重试使用同一键和相同内容。ID 与金额在返回 JSON 中统一为字符串。

| 功能 | 请求及具体输入 | 关键预期 |
| --- | --- | --- |
| 设置 PIN | POST `/sandbox/wallet/setup`，`{"loginPassword":"本人登录密码","pin":"123456","confirmation":"123456"}` | `configured=true,balance="0.00",currency="CNY"`；已配置不允许再次初始化 |
| 模拟充值 | POST `/sandbox/wallet/credits`，`{"amount":"1000.00","pin":"123456"}`，`Idempotency-Key: wallet-credit-001` | 余额与 CREDIT 流水更新一次；重放不重复充值 |
| 建付款尝试 | POST `/payment-orders/P/attempts`，`{"amount":"200.10","method":"Alipay"}`，`Idempotency-Key: pay-001` | 应付单 `provider="WIREMOCK"`；新增尝试含 `id/outTradeNo/status` |
| 密码授权 | POST `/sandbox/payment-attempts/A/authorize`，`{"pin":"123456"}` | 扣款只发生一次；业务状态可暂为 PENDING，等待回调/查询 |
| 查询/核验 | GET `/payment-orders/P`；POST `/payment-orders/P/refresh` | 原支付单与尝试；确认后 `status="SUCCEEDED"` |
| 关闭尝试 | POST `/sandbox/payment-attempts/A/cancel`，无正文 | 渠道 CLOSED 或按实际 PAID 核验；不会把已付交易回退 |
| 钱包流水 | GET `/sandbox/wallet/entries?page=0&size=20` | 每条包含字符串 `id/amount/balanceAfter` 及 `kind/reference/createdAt` |
| 退款状态 | GET `/refunds/R`；POST `/refunds/R/refresh` | `id/amount` 均为字符串，状态按渠道实际结果更新 |

普通响应包装为 `{"data":...}`，错误含 `code/message/traceId`。金额 `200.09` 与应付 `200.10` 不一致应拒绝；浏览器不能传入 `paid=true` 或调用一个无密码成功入口。

## 4. 可控故障与恢复

先正常创建尝试，从界面取得真实 `outTradeNo`，把下面的 `HB实际交易号` 替换掉。脚本只修改该交易、该操作的 WireMock 覆盖，不碰钱包/预订，也不会重置别人的场景：

```powershell
python scripts/Set-PaymentScenario.py --trade HB实际交易号 --operation authorize --scenario declined
python scripts/Set-PaymentScenario.py --trade HB实际交易号 --operation query --scenario unavailable
python scripts/Set-PaymentScenario.py --trade HB实际交易号 --operation callback --scenario unavailable
# 恢复指定操作；其他操作的故障仍保留，需要分别恢复
python scripts/Set-PaymentScenario.py --trade HB实际交易号 --operation callback --scenario normal
```

| 操作/场景 | 应观察到什么 | 如何恢复 |
| --- | --- | --- |
| authorize / declined | 明确拒绝，新扣款为 0 | 恢复 normal 后用原尝试授权 |
| authorize / unavailable 或 slow | 网络错误，不执行钱包事务 | 恢复 normal；原尝试仍可查询 |
| query / unknown、unavailable、slow | 返回待确认/核验错误；不得据此宣告成功或释放占房 | 恢复 normal，查询原单 |
| callback / unavailable | 扣款与事件已持久化，通知暂未确认 | 恢复 normal 等重试，或主动刷新原支付单 |
| callback / slow | 可出现迟到或重复事件 | 同一交易仍只能确认一次 |
| refund / unavailable | 退款保持待确认，不错误增加余额 | 恢复 normal，以原退款号核验 |
| WireMock 重启 | 只影响通道可用性，MySQL 记录应保留 | 恢复容器后查询；不得清库重新付款 |

故障注入面仅为开发机 `127.0.0.1:9090` 的管理端。部署版 WireMock 不发布端口，Nginx 拒绝管理和本地回调路径；需要部署环境排错时由运维在私网执行，不把管理端开放给浏览器。

逐交易故障覆盖只驻留 WireMock 内存，重启后恢复静态正常映射；资金、交易与回调队列保存在 MySQL，不依赖这些故障覆盖持久化。

支付/退款自动恢复有逐笔租约、退避和 12 次失败预算；健康的正常待付查询不会耗尽失败预算。回调队列最多尝试 8 次，超过预算进入人工 REVIEW。管理员在“支付异常复核”页面看到恢复任务，检查故障后重新开放。该操作仅允许再核验，不把付款/退款直接改成成功。熔断按渠道在单实例内运行：连续 5 次故障打开 30 秒，再允许一个半开探测；多实例不共享熔断内存，但共享数据库恢复租约。

## 5. DirectMail 与三角色邮箱

酒店统一 From 使用已验证发信地址和对应 SMTP 密码，不用顾客邮箱冒充发件域。业务发件人来自已登录账户，放在 Reply-To；收件人来自已注册账户，由后端查库确认。所有角色都可以写自己的站内邮件；管理员审计全部消息，不共享其他人的登录凭据。

确认通知和 D3/D1 提醒也使用同一个 DirectMail 适配器。通知/个人邮件分别持久排队，发送网络请求在事务外；共同日预算中至少预留 1 封、通常 20% 给系统通知。账户个人发信仍有每小时限流。预留额度不是服务商费用额度，需同时监控 DirectMail 控制台。

| 结果 | 保存状态/处理 |
| --- | --- |
| SMTP 正常返回 | SENT，仅证明服务接受；用户站内收件副本可见 |
| 配置禁用、认证/准备错误、保留测试域名 | FAILED，先纠正原因，再显式重试 |
| 可证明连接未建立 | RETRY，1/5/30 分钟有限退避，之后停止 |
| 超时/断连且不能证明未接受 | UNKNOWN，先检查服务商记录/收件箱，人工确认后才重发 |
| 服务商接受后退信/投诉 | 目前未接入自动反馈，不能自动标为已送达或已退信 |

`SENT` 不等于 `DELIVERED`，入站回复同步和 DirectMail 退信/投诉事件仍是明确待完善项。本轮没有声称实现或验证未配置的供应商事件 API。自动投递阻止 `.test/.invalid` 和常见 example 保留地址，旧种子数据不会向真实 SMTP 发信。不要把收件 allowlist 中的测试限制误认为整个系统只有两个固定邮箱。

独立检查不用 Docker/MySQL：

```powershell

# 仅自己需要再次实际收件验证时显式执行，一次发一封
python scripts/Test-DirectMail.py --recipient 你控制的真实邮箱
```

## 6. 验证顺序和安全边界

先执行 `Test-Backend.ps1 -Modules PaymentProtocol`，再运行隔离 MySQL 的 Identity、Booking、SandboxPayment、Changes、Mail、Notification，最后在工作环境按第 3–5 节验收。全部测试输入/预期在[两阶段测试表](testing/README.md)；真实容器与收件结果应另存本轮 results，不能用协议单元测试代替。

不要提交 `.env`、真实 SMTP/回调秘密、演示密码、数据库备份；不要把它们变成 `VITE_*`。轮换回调密钥时暂停回调调度，更新后端配置并重启，队列下一次发送会重新签名。WireMock 通信限定回环/容器私网；对外发布网页需要 HTTPS 和安全 Cookie。本地支付沙箱即使运行在部署容器，也不成为可处理真实银行卡资金的系统。

实现使用 WireMock 官方[Docker 运行](https://wiremock.org/docs/standalone/docker/)和[响应/代理模板](https://wiremock.org/docs/response-templating/)能力；SMTP 产品配置以[阿里云邮件推送文档](https://help.aliyun.com/zh/direct-mail/)及用户账户实际区域/配额为准。
