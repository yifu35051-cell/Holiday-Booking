# Docker MySQL 与后端一键启动

更新日期：2026-10-26。适用于 Windows PowerShell 5.1 + JDK 21 + Docker Desktop。

**首次编辑一次配置文件，以后每次只运行一个命令。** MySQL 在容器中运行，Java 后端在 Windows 上运行，无需安装本地 MySQL，也无需每次手动设置环境变量。

## 1. 日常只需这一条命令

在项目根目录 Holiday-Booking 执行：

~~~powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\Start-Backend.ps1
~~~

脚本会依次：

1. 读取根目录 .env.mysql，校验配置、JDK 21 和 Docker Compose。
2. 检查 Docker Linux 引擎；若未启动，尝试启动已安装的 Docker Desktop 并等待就绪。
3. 启动或复用 MySQL 容器，等待实际数据库连接健康检查通过。
4. 从同一份配置生成 JDBC 地址和密码，在前台运行 Spring Boot。

正常启动后保留这个终端，另开终端测试接口。ExecutionPolicy Bypass 仅作用于当前子 PowerShell 进程，不改变系统永久执行策略。

如果当前终端已允许执行本地脚本，也可以直接运行：

~~~powershell
.\scripts\Start-Backend.ps1
~~~

## 2. 首次准备环境和配置

### 2.1 环境只安装一次

- 安装 JDK 21，确保 JAVA_HOME 和 PATH 指向 JDK 21。
- 根据 [Docker Desktop Windows 官方说明](https://docs.docker.com/desktop/setup/install/windows-install/) 安装 Docker Desktop，启用 WSL 2 和 Linux containers。
- Docker Desktop 首次安装后的授权、初始化、WSL 安装及可能的系统重启，需要先在界面中完成；脚本只尝试启动已经安装好的程序。
- 首次构建需要下载 Maven、Java 依赖和 MySQL 镜像，需网络可用。

~~~powershell
java -version
docker version
docker compose version
~~~

docker version 的 Server 部分正常才代表引擎可用。访问 Docker 命名管道被拒绝时，应先解决当前 Windows 账号访问 Docker Desktop 的权限，脚本不会自动提权或重置 Docker。

### 2.2 只编辑一个配置文件

| 文件 | 用途 |
| --- | --- |
| [.env.mysql.example](../.env.mysql.example) | 可提交的配置模板，不包含真实密码 |
| .env.mysql | 你自己的数据库和后端启动配置；根目录 .gitignore 已忽略 |
| [Start-Backend.ps1](../scripts/Start-Backend.ps1) | 读取文件、启动容器、等待数据库、启动 Java |
| [compose.mysql.yaml](../compose.mysql.yaml) | MySQL 8.4、端口、数据卷、字符集与健康检查 |

已有 .env.mysql 时保留原文件，**不要覆盖已经使用的数据库密码**。尚未创建时，执行一次：

~~~powershell
if (-not (Test-Path .\.env.mysql)) {
    Copy-Item .\.env.mysql.example .\.env.mysql
}
notepad .\.env.mysql
~~~

配置示例，密码必须替换成自己的实际值：

~~~dotenv
# 数据库：已有数据卷时保持现有密码。
MYSQL_ROOT_PASSWORD='填写数据库root密码'
MYSQL_PASSWORD='填写应用数据库密码'
MYSQL_PORT=3307

# Java HTTP 端口。
SERVER_PORT=8080

# 可选：仅显式使用 -InitializeAdmin 时读取，普通启动无需填写。
BOOTSTRAP_ADMIN_EMAIL=''
BOOTSTRAP_ADMIN_PASSWORD=''
~~~

旧配置只有三个 MYSQL_* 字段也可以启动；SERVER_PORT默认8080，管理员字段默认空。新库、旧库的普通启动都不要求管理员信息，即使旧文件只填了其中一项也会忽略。无需重建数据库：

~~~dotenv
BOOTSTRAP_ADMIN_EMAIL=''
BOOTSTRAP_ADMIN_PASSWORD=''
~~~

| 配置项 | 用途和默认值 |
| --- | --- |
| MYSQL_ROOT_PASSWORD | MySQL root 密码，只供数据库管理，Java 不用它连接 |
| MYSQL_PASSWORD | holiday_booking 应用账户密码；脚本同时用于容器和 Java |
| MYSQL_PORT | Windows 映射端口，默认 3307；容器内部固定 3306 |
| SERVER_PORT | 后端 HTTP 端口，默认 8080 |
| BOOTSTRAP_ADMIN_EMAIL / BOOTSTRAP_ADMIN_PASSWORD | 普通启动忽略；加 -InitializeAdmin 时必须同时填写有效值 |

管理员密码需 12–72 字符，UTF-8 编码不超过 72 字节。**初始化不会重设已有管理员的密码**，也不会把同邮箱普通账户升级成管理员。

仅当需要创建开发库管理员时，填好上面两个管理员字段后运行：

~~~powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\Start-Backend.ps1 -InitializeAdmin
~~~

之后恢复普通启动命令即可。顾客、员工、管理员的功能及测试见[角色功能与测试](README.md#roles)。Java测试会在独立临时MySQL中创建测试角色，不使用这里的管理员账户或开发库。

文件采用简单、明确的格式：

- 每行一个 KEY=value；空行和单独以 # 开头的注释行会被忽略。
- 密码使用单引号，$、#、空格和反斜杠按原样读取，不执行变量替换或脚本。
- 当前不支持值内部的单引号、多行值、双引号、行尾注释、export 或额外未知字段。
- 不要把文件当作 PowerShell 脚本执行，也不需要手动导入。
- 脚本以文件中的值为准，在本进程覆盖对应旧环境变量，退出时恢复；不修改 Windows 用户或系统环境变量。

### 2.3 仅校验，不启动服务

~~~powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\Start-Backend.ps1 -CheckOnly
~~~

这会检查配置格式、必填值、端口、JDK 21、Compose 及 YAML 配置。不启动容器或 Java，也不验证数据库里的密码是否与文件一致。

需要使用另一份符合相同格式的文件时：

~~~powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\Start-Backend.ps1 -ConfigFile 'D:\local-config\holiday.env'
~~~

默认路径根据脚本所在位置解析；从其他工作目录用脚本的绝对路径运行，也能找到本项目。自定义 ConfigFile 的相对路径则相对于调用终端的位置。

## 3. 启动后发生什么

~~~text
.env.mysql
  ├─ MYSQL_* → Docker Compose → MySQL 8.4
  └─ MYSQL_PASSWORD + MYSQL_PORT → Java JDBC 配置
                                  ↓
                       Flyway 迁移 + Hibernate 校验
                                  ↓
                       Spring Boot HTTP 服务
~~~

例如 MYSQL_PORT=3307 时，脚本自动生成：

~~~text
DB_URL=jdbc:mysql://127.0.0.1:3307/holiday_booking?connectionTimeZone=UTC&forceConnectionTimeZoneToSession=true
DB_USERNAME=holiday_booking
DB_PASSWORD=与 MYSQL_PASSWORD 相同
~~~

你不需要在文件中额外配置 DB_URL 或重复保存数据库密码。修改 MYSQL_PORT 后重新运行脚本即可，Java 和 Compose 会一起使用新端口。

当前脚本专门服务于“先完成数据库及其他业务”的开发阶段，固定采用以下运行模式：

| 运行设置 | 脚本使用值 |
| --- | --- |
| SPRING_PROFILES_ACTIVE | local |
| PAYMENT_MODE / EMAIL_MODE | disabled |
| JOBS_ENABLED | false |
| MAIL_HEALTH_ENABLED | false |

因此不会调用真实或模拟支付成功流程，也不会发送邮件。数据库健康探测保持启用；报价、待支付预订、会员购买单等仍走原有业务事务。

JOBS_ENABLED=false 同时暂停超时回收任务，未支付预订的占房可能超过 15 分钟仍保留。本轮不验收支付恢复或自动回收；后续恢复相关功能时需调整这份本地启动脚本的运行模式。

首次空数据卷启动时，MySQL 官方镜像创建 holiday_booking 数据库和应用账户；Java 启动后 Flyway 创建业务表与 JDBC 会话表。无需再手动执行 CREATE DATABASE / CREATE USER。镜像初始化变量不会给已有数据卷重设密码，见 [MySQL 官方镜像说明](https://hub.docker.com/_/mysql)。

脚本只在数据库健康检查成功后启动 Java。健康检查会实际执行 SELECT 1；容器创建和端口配置可参考 [Compose 服务配置](https://docs.docker.com/reference/compose-file/services/)。

## 5. 停止、重启和数据保留

| 场景 | 操作 |
| --- | --- |
| 每天启动数据库和后端 | powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\Start-Backend.ps1 |
| 停止 Java | 在运行脚本的终端按 Ctrl+C；原有 cmd Wrapper 若询问是否终止批处理，确认结束 |
| 只重启 Java | 停止后重新执行启动脚本，已有健康数据库容器会复用 |
| 查看数据库 | docker compose --env-file .env.mysql -f compose.mysql.yaml ps |
| 查看数据库日志 | docker compose --env-file .env.mysql -f compose.mysql.yaml logs --tail 100 mysql |
| 停止数据库 | 先停止 Java，再执行 docker compose --env-file .env.mysql -f compose.mysql.yaml stop |
| 查看数据卷 | docker volume inspect holiday-booking_mysql-data |

Ctrl+C 停止前台 Java，**不会自动关闭或删除数据库**。脚本没有清库逻辑，也不会对数据卷执行删除。数据保存在 holiday-booking_mysql-data；普通 stop / down 会保留数据，不要在日常 down 命令后添加 -v。

首次下载依赖或迁移耗时不等于卡死，请查看当前 Maven / Spring Boot 日志。脚本最后会一直留在前台展示应用日志，这是正常行为。

## 6. 常见问题

| 现象 | 处理 |
| --- | --- |
| 配置文件不存在或仍有 REPLACE_WITH 占位值 | 编辑 .env.mysql，填写自己的密码；不要覆盖已有数据库密码 |
| 新数据库没有管理员 | 不影响普通启动；需要时填写两个 BOOTSTRAP_ADMIN 字段，再加 -InitializeAdmin 启动 |
| Docker Desktop 未启动 | 脚本尝试启动默认安装路径下的程序；首次初始化或自定义安装位置需手动打开 |
| Docker engine access denied | 当前账号无法访问 Docker 管道；检查 Docker Desktop 登录会话与权限，不是数据库密码错误 |
| Docker 引擎一直不就绪 | 打开 Docker Desktop 检查 WSL 和 Linux containers；脚本不会自动重装 WSL |
| 3307 已被占用 | 在文件中换一个 MYSQL_PORT，重新运行脚本，JDBC 地址会自动同步 |
| 8080 已被占用 | 先停止旧后端，或修改 SERVER_PORT；脚本会拒绝启动第二个占用同端口的 Java |
| MySQL 不 healthy / Access denied for user | 查看容器日志，确认文件密码等于数据卷中已有账户的密码；改文件不会重设数据库密码 |
| 手动 Compose 命令与脚本行为不同 | 手动 Compose 会优先使用当前终端的同名环境变量；启动脚本会以文件中的值覆盖 |
| Public Key Retrieval is not allowed | 先确认连接的是本机容器并检查 MySQL TLS 配置；当前脚本不自动放宽生产连接策略 |
| Flyway 校验失败 | 查看应用日志和历史迁移修改；不要删除迁移记录或关闭校验掩盖问题 |
| 修改管理员密码后旧密码仍生效 | BOOTSTRAP 只负责初始化；已有用户密码不会被它重置 |
| 直接用 IDE / mvnw 启动未读取文件 | .env.mysql 由启动脚本加载；直接绕过脚本时需要自行配置 IDE 运行环境 |

## 7. 测试启动、登录与 API 文档

### 为什么测试时又出现启动日志

| 使用方式 | 实际运行位置 | 数据与会话 |
| --- | --- | --- |
| `Start-Backend.ps1` | 常驻 HTTP 服务，默认 localhost:8080 | 开发 MySQL；浏览器各自保存登录 Cookie |
| `Test-Backend.ps1` | 每模块独立 Maven/JVM；Spring 测试上下文，默认不监听 8080 | Testcontainers 临时 MySQL；测试自行创建账户及会话 |
| `scripts/backend-tests/Run-BackendTests.ps1` | HTTP 请求访问已启动的 8080 服务 | 使用开发库，脚本独立保存 Cookie；会写入测试数据 |

Java 测试只需 Docker 可用，不必提前启动开发后端；已启动也可以保留。每个阶段会重新执行所选模块；当前脚本每模块一个 Maven 进程，不跨模块缓存 Spring 上下文。同一模块内不同上下文也可能分别建库，因此启动较慢是当前隔离策略的代价。测试结束不向开发库保留测试账户、预订或浏览器会话。

`@SpringBootTest` 默认使用 MOCK Web 环境，加载应用组件而不启动 HTTP 监听；MockMvc 在进程内调用过滤器和控制器，Service 用例直接调用业务服务，数据库仍是真实 MySQL。[Spring Boot 官方说明](https://docs.spring.io/spring-boot/4.2/reference/testing/spring-boot-applications.html)

已核对 `results/java-20261027-164758-848-4afc50/`：8 个单模块共 42 项通过，失败/错误/跳过均为 0；创建 10 个测试 MySQL 容器。Identity 和 Payment 各有两个上下文，其余每模块一个。日志中的 MySQL 随机端口（如 53334、51192）不是开发服务端口。尚无这次集成阶段 9 项的执行记录，不能据此称全部阶段验收完成。支付/通知通过的仍是本地模拟测试。

日志里的 `test.results.directory overwritten` 是脚本覆盖报告路径的提示；MySQLDialect 是可自动推断的冗余配置提示；Byte Buddy 动态代理提示来自测试工具。此次均未导致失败，不表示后端重启异常。

### 8080 应该访问哪些地址

| GET 地址 | 未登录时的预期 |
| --- | --- |
| `http://localhost:8080/actuator/health` | 健康时 200 |
| `http://localhost:8080/api/v1/room-types` | 200；开发库没有房型时列表为空 |
| `http://localhost:8080/api/v1/auth/csrf` | 200；返回 `data.headerName` 和 `data.token` |
| `http://localhost:8080/api/v1/auth/me` | 401，登录后返回本人 |
| `http://localhost:8080/swagger-ui/index.html` | 401；管理员登录后可查看交互式 API 文档 |
| `http://localhost:8080/v3/api-docs` | 401；管理员登录后可读取 OpenAPI JSON |

2026-10-27 只读访问核验：health、room-types 为 200，me、Swagger 为 401，与当前权限配置一致。Swagger UI 展示路径、方法、参数和模型，OpenAPI JSON 可导入接口工具；自动生成的说明不保证完整表达业务规则、全部错误码和权限矩阵。[springdoc 官方文档](https://springdoc.org/)

根路径 `/` 没有前端首页，`/login` 没有登录页面。地址栏只能发 GET，登录接口要求 **POST /api/v1/auth/login**，不能通过直接打开该地址登录。未登录访问不存在的受保护路径，也可能在路由处理之前被安全过滤器返回 401。

### 在同一个浏览器中登录并打开 Swagger

1. 先确认开发库已有管理员。没有时按前文填写 `.env.mysql` 的两个 BOOTSTRAP 字段，停止原开发后端，再用 `Start-Backend.ps1 -InitializeAdmin` 启动。普通注册只创建 CUSTOMER；测试管理员不在开发库中。
2. 在浏览器打开 `http://localhost:8080/api/v1/auth/csrf`，再打开开发者工具的 Console。以下代码仅调用本项目接口；邮箱与密码由弹窗输入，不要把真实密码写进代码。**浏览器 prompt 的密码输入会明文显示，请在私密环境操作。**
3. 执行以下代码，登录成功会自动跳转 Swagger。始终使用 `localhost`，不要中途切换 `127.0.0.1` 或无痕窗口。

```javascript
(async () => {
  const email = prompt('开发库管理员邮箱');
  const password = prompt('管理员密码（输入会明文显示）');
  if (!email || !password) return;
  const csrfResponse = await fetch('/api/v1/auth/csrf', {
    credentials: 'same-origin'
  });
  if (!csrfResponse.ok) throw new Error(`获取 CSRF 失败：${csrfResponse.status}`);
  const { data: csrf } = await csrfResponse.json();
  const response = await fetch('/api/v1/auth/login', {
    method: 'POST',
    credentials: 'same-origin',
    headers: {
      'Content-Type': 'application/json',
      [csrf.headerName]: csrf.token
    },
    body: JSON.stringify({ email, password })
  });
  const result = await response.json();
  if (!response.ok) throw new Error(`${response.status}: ${result.message}`);
  if (result.data.role !== 'ADMIN') throw new Error('已登录，但该账户不是 ADMIN');
  location.assign('/swagger-ui/index.html');
})().catch(error => console.error(error.message));
```

这会把登录 Cookie 保存在当前浏览器。PowerShell、Postman、Java 测试和浏览器不共享 Cookie；在其他工具登录不会让浏览器自动登录。当前使用 Session 认证，不是 Bearer JWT，不能用随意填写的 Authorization token 代替 Cookie。

Swagger **查看协议和 GET 请求**可使用当前会话。当前尚未配置 Swagger 对 Session CSRF 的自动附加，所以 Try it out 的 POST/PUT/DELETE 可能返回 403。手动写请求必须在登录后重新 GET `/api/v1/auth/csrf`，带同一会话 Cookie，并将返回的 `headerName: token` 加到请求头；登录前的 token 已失效。不要为此关闭 CSRF。项目使用 `HttpSessionCsrfTokenRepository`，不能直接套用依赖 `XSRF-TOKEN` Cookie 的配置。

遇到 401，检查是否使用开发库账户、是否保留同一会话；403 检查角色及 CSRF；管理员已登录仍无法找到文档时，检查启动环境的 `API_DOCS_ENABLED` 是否关闭、路径及服务启动日志。完整 HTTP 冒烟命令见[脚本说明](../scripts/backend-tests/README.md)，它用于验证正在运行的开发服务。

## 8. 启动脚本的历史验证边界

本次已用现有 .env.mysql 完成配置与 Compose 解析检查，保留既有数据库密码和 3307 端口。启动控制流程和异常路径使用替身命令进行验证，不修改真实数据库。

此前启动脚本开发时，工具环境访问 Docker Linux 引擎返回 Access is denied，未完成当时的真实容器与 Java 端到端启动验收。后续用户提供的 MySQL 测试记录与本次 8080 只读检查见第 7 节；这些证据不等于启动脚本全部分支均已验收。CheckOnly 通过本身也不代表服务已经启动。

该脚本是本地开发入口，完整生产部署仍需单独配置。
