# 整改实施审查与 Appendix 2 收敛核对

审查基线：2026-11-07 当前工作副本；对照 [原逐节清单](Design-Report-逐节审查与改进清单.md)、SRS v2.0 与根目录 Appendix 2。本文记录实施/验证状态；[当前设计基线](Current-Design-Baseline.md)负责说明架构、对象与契约，避免两份文件重复充当成品报告。

**结论：主要 P1 代码/配置缺口已整改，WireMock + DirectMail 已接入当前运行配置；尚不能宣称系统或 Appendix 2 最终报告已全部验收收敛。** 本轮 Docker 引擎未运行，未执行工作库迁移、真实 WireMock/MySQL 全链路或真实业务邮件投递。P2 的供应商反馈、数据生命周期执行、告警、性能/可访问性证据及最终报告编排仍有明确缺口。

## 1. 范围修订及执行顺序

用户已明确放弃第三方支付，指定 WireMock 本地支付；DirectMail 仍是真实第三方邮件目标。因此原 S03–S06/S10 中“开通第三方支付账号、支付宝隧道、真实付款二维码”的任务被本期本地服务虚拟化取代，不再作为阻塞项。资金正确性、幂等、恢复、权限、协议和测试要求完整保留。不能把 WireMock 描述为已经接通的支付供应商。

本轮先处理角色、匿名浏览和 DTO 等 P1，再改造支付/邮件装配与关键安全恢复，随后处理查询、模板、观测和文档。未修改已执行 V1–V5；升级通过新增 V6。

状态用语：**已实现**表示有代码/配置，**已检查**表示对应检查本轮执行成功，**待验收**表示缺真实运行证据；**部分**表示仍有实现或正式设计材料缺口，不能视为关闭。

## 6. 剩余工作顺序与关闭标准

1. **先完成当前P1实机闭环。** 启动Docker后准备WireMock镜像和本次更新的应用包；先跑隔离MySQL，再验正常付款/查询/关单/退款、三角色权限、DirectMail三角色与确认/D1实际收件。保存版本、脱敏交易/消息标识和收件确认；不要再将示例域名当互联网收件人。
2. **随后完成P2一致性/运营证据。** 按[故障指南](../支付与邮件部署.md#4-可控故障与恢复)逐交易注入拒绝、503、慢响应、回调丢失，重启依赖/工作者，检查只扣/退一次、UNKNOWN不误放房、预算耗尽与管理员恢复。测试当前V6约束及历史MOCK数据兼容。
3. **补齐尚缺实现。** 根据DirectMail实际授权方式设计反馈/抑制，不虚构已配置API；确定保留期后实现受控脱敏/清理并证明不破坏幂等/外键；配置指标报警接收端。现有SMTP真实投递可使用，不因反馈缺失改回Mailpit。
4. **完成NFR与交付检查。** 在SRS规定环境跑50并发/5分钟、100房/10000预订，记录p95和5xx；键盘/200%缩放、酒店异地时区；隔离恢复与跨机器镜像首次启动。发布前冻结镜像、检查秘密、配置HTTPS。
5. **最后生成Appendix 2成品。** 从当前基线选图和正文，完善完整类/CRC/状态/数据字典，压到课程页数，保留真实证据及明确限制，再由团队签核。当前只生成审查和设计基线，未冒充已提交设计报告。

只有以上对应项关闭，才能把“代码已写/配置已放好”升级为“已验证”，并判断最终设计文档是否达到提交标准。
