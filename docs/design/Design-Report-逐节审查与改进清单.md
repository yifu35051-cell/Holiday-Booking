# Design Report 逐节审查与改进清单

> **本清单保留原始审查/优先级，以下“未实现/现有”是当时基线，不代表整改后的当前状态。** 2026-11-07 本轮已实施 WireMock 本地支付、DirectMail 替代、P1 权限/契约及部分 P2 改进；逐项实施/验证与未关闭项请看 [Implementation Review](Implementation-Review.md)，对应设计见[当前基线](Current-Design-Baseline.md)。第三方支付账号/公网隧道已按用户决定退出本期范围，第三方邮件仍采用 DirectMail。

审查日期：2026-11-07。对照材料：根目录 `Appendix 2. Object_Oriented_Design_Report_Template condensed v2.pdf` 全部 17 页，以及 Requirements Specification v2.0、当前 Java/Vue 源码、Flyway V1–V5、Compose、现有设计资料和 `results/`。

**最新范围修订：用户已放弃第三方支付，目标改为本地模拟真实支付流程，不再依赖外部支付账号或公网隧道。** 推荐复用现有持久化钱包，补渠道事件、故障场景和退款恢复，见[支付指南1.5](../支付与邮件部署.md#15-最新本地支付选型现有钱包--持久化渠道模拟--可控故障)。此次按支付范围理解调整，DirectMail不擅自改回Mailpit。下文第四节的第三方支付选型/账号/隧道任务保留为历史对照，不再是本期支付前置条件；其中资金正确性、幂等、恢复、权限与测试要求仍然适用。

**DirectMail专项进展（2026-11-07）：** `development.env`中的Spring YAML已转换为项目支持的dotenv，保留原SMTP发信地址与密码。独立脚本已通过DNS、TLSv1.3、SMTP认证（235）并提交一封指定QQ收件人的验证邮件，详见[实际记录](../../results/directmail-20261107T073805347998Z.json)和[邮件指南第8节](../支付与邮件部署.md#8-directmail独立验证与单一发信地址的角色设计)。此项仅证明传输配置可用；收件人确认、完整后端业务、Docker第三方装配、三角色消息及反馈处理仍待核验。S07/S10不能据此全部标为完成。

**结论：系统已具备主要业务模块，但还不能直接用现有技术文档作为符合 Appendix 2 的成品设计报告。** 目前同时存在三类问题：部分业务/接口与 SRS 不一致；对象职责、集成故障处理和性能设计仍有缺口；设计图、CRC、追踪及验证证据落后于代码。应先解决明确的不一致，再按真实实现补齐报告，不能只把旧文档重新排版。

本次只审查并提出措施，未修改业务代码、启动容器或执行测试。下文“已有”表示存在代码或资料，不等于当前版本已验收通过；静态推导的问题均未冒充运行复现结果。未读取实际环境文件中的凭据。

## 阅读方式与优先级

| 标记 | 意义 |
| --- | --- |
| 实现 | 需要修改 Java、Vue、SQL 或运行配置 |
| 设计 | 需要确定对象、契约、边界或恢复策略；部分随后落到代码 |
| 文档 | 实现可能已有，但缺少与代码一致的设计表达 |
| 证据 | 缺少与当前版本对应的验证记录；不能据此断言功能失败 |
| P1 | 优先解决明确的需求/契约不一致、影响正常使用的问题，以及完成第三方支付/邮件的必要接入闭环 |
| P2 | 完成正式设计基线前补齐的结构、可靠性和验证措施 |
| P3 | 超出已选第三方接入范围的扩展，例如额外供应商或SMS；不能再把第三方支付/邮件本身归到这里 |

这里的 P1/P2 是整改顺序，不是 SRS 的 Must/Should 优先级，也不是漏洞等级。

## 一、先明确哪些不应被误判为缺失

| 已有基础 | 可以确认的实现 | 本轮处理原则 |

Five traps逐项结论：

1. **超时被当成失败付款：** 当前UNKNOWN及对账思路正确，保留并补故障类型/恢复证据，不应删掉UNKNOWN。
2. **浮点金额：** 后端BigDecimal/DECIMAL已有，不能误判已用double计价；报价层也已有零金额拒绝。需补边界证据，修复退款JSON类型不一致。
3. **厂商模型泄入领域：** 未见领域导入Alipay SDK，这是已有优点；仍须补映射测试和清楚的错误契约。
4. **外部调用放在事务内：** 支付/SMTP主要路径已分离；钱包同库调用参与原子事务是合理例外，不应机械移出。增加边界检查防止未来把网络适配器放回锁内。
5. **假定免费层稳定：** 当前自建依赖有资源/磁盘上限；目标第三方必须同时核定配额、计费、限流和退路，不假定免费层稳定。

**P1闭环的最低含义：** 供应商系统中确有交易/投递记录；系统核验后只推进一次业务；失败/未知不误报成功；用户有可操作的付款和结果界面；不是“SDK已添加”“SMTP配置可填”或“本地测试通过”。

### 4.2 服务选型与技术栈需要补齐的决定（S01 / P1）

**无自备公网IP的补充研究：** [支付指南第9节](../支付与邮件部署.md#9-无自备公网ip的第三方支付选型分析)对比了Stripe官方Sandbox+CLI、PayPal Sandbox、Alipay+HTTPS中继及本地mock。若可取得合适测试账号，Stripe+CLI在本地完整事件转发方面优先；PayPal更接近买家/商家账户体验，但不能忽略真实webhook可达性和CNY账户限制。此为待可行性验证的候选，不表示已替换供应商或放宽Alipay/Wechat课程契约。S01/S03须据最终选择更新，不能把“没有自备公网IP”与“必须放弃第三方支付”等同。

### 4.4 对现有实现的具体复用与必要改造

- **不新建第二套支付业务模块。** 保留PaymentGateway、PaymentService、RefundService、业务状态机及事务编排；完善第三方适配器、渠道身份和错误结果。MockPaymentGateway/SandboxWalletService仅用于显式本地模式，不成为在线失败后的自动回退收款渠道。
- **不另建重复通知模块。** notification继续负责预订确认/提醒，mail继续负责个人邮件与共同传输；第三方SMTP接在现有EmailSender后。反馈处理与模板可以在mail内按职责增加，不能复制整套发送队列。
- **前端既要适配第三方，也要保持角色隔离。** 顾客完成付款，员工处理允许范围内的通知任务，管理员查异常与邮件审计；三者都使用自己的站内邮箱。管理员不是凭前端按钮就能绕过供应商资金规则。
- **部署仍区分首次构建和日常启动。** 第三方参数集中在config模板中，秘密用外部文件/secret注入；首次准备镜像后日常直接运行。切换配置可能需要重建容器以加载新值，不等于重新构建镜像。

### 4.6 本次仍不强制新增的范围

- SMS、外部旅游portal、第二供应商、Redis/Kafka、微服务仍是范围外扩展；第三方支付和邮件本身已不在此列。
- 多币种、银行卡tokenisation、强制所有电话E.164等，须按最终支付产品与业务需求决定，不机械照抄模板。
- 真实资金结算与商用上线资格需要单独确认；课程第三方官方沙箱联调不等于已获准真实收款。
- 站内个人邮箱不自动等于托管完整互联网邮箱；互联网入站回复若要加入，需独立明确需求和接入能力。

## 五、故障模式表应如何补齐

下表是建议加入设计报告4.4的项目化内容；“需补”表示没有足够实现/证据，不是已经运行通过。

| 依赖/故障 | 用户应看到什么 | 恢复与一致性 | 当前审查结论 |
| --- | --- | --- | --- |
| 付款已扣款但结果落账前中断 | 处理中/待核实，不引导再次扣款 | 原tradeNo查询恢复；幂等流水仅扣一次；UNKNOWN期间不释放占房 | 核心机制已有，需补重启/失败链证据 |
| 第三方支付回调未到/重复/迟到 | 查询到最终状态；重复不再发权益 | 主动对账；迟到异常保留资金证据，不强行确认失效预订 | 代码已有主要路径，仍须第三方真实合同验证 |

| SMTP接受后断连或worker崩溃 | UNKNOWN并提示可能已投递 | 不自动重发；人工确认后再发，审计保留 | 租约/UNKNOWN机制已有，故障注入需补 |
| SMTP日预算耗尽 | 明确排队原因与后续计划 | 下个预算窗口恢复；关键系统提醒有预留/优先级 | 共享预算已有，原因展示/优先级需补 |
